# Helidon Services Maven Plugin

The `io.helidon.build-tools:helidon-services-plugin` generates `META-INF/services`
files from the `provides ... with ...` directives in a compiled Java module
descriptor. This lets a modular JAR expose the same service providers when used
on the class path with `ServiceLoader`.

## Goal: `services`

The goal reads `${project.build.outputDirectory}/module-info.class`, normally
`target/classes/module-info.class`, and writes one file per service under
`target/classes/META-INF/services`. Each file contains the service's provider
class names, one per line, preceded by an optional comment. Maven includes these
files in the JAR during packaging.

The default lifecycle phase is `compile`. The module descriptor must already be
compiled when the goal runs. Bind the execution to `process-classes` as shown
below to ensure it runs after compilation and before packaging.

### Build configuration

Declare the plugin under `build/plugins` with an execution of the `services`
goal. A declaration under `pluginManagement` alone does not execute the plugin.
Set `helidon.build-tools.version` to the build-tools version you use; it is
independent of your application's Helidon version.

```xml
<project>
    <!-- ... -->
    <build>
        <plugins>
            <plugin>
                <groupId>io.helidon.build-tools</groupId>
                <artifactId>helidon-services-plugin</artifactId>
                <version>${helidon.build-tools.version}</version>
                <executions>
                    <execution>
                        <id>generate-services</id>
                        <phase>process-classes</phase>
                        <goals>
                            <goal>services</goal>
                        </goals>
                    </execution>
                </executions>
            </plugin>
        </plugins>
    </build>
</project>
```

For example, a module declaration containing:

```java
provides com.example.Greeting with com.example.EnglishGreeting,
                                  com.example.FrenchGreeting;
```

produces `target/classes/META-INF/services/com.example.Greeting`:

```text
# This file was generated by Helidon services Maven plugin.
com.example.EnglishGreeting
com.example.FrenchGreeting
```

Run `mvn package` to compile the descriptor, generate the service files, and
include them in the JAR. With the `process-classes` binding above, `mvn compile`
alone does not execute the goal.

### Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `skip` | boolean | `false` | Skip the goal, including the module descriptor check. |
| `failOnMissingModuleInfo` | boolean | `true` | Fail if sources exist but the compiled `module-info.class` is missing. Set to `false` to skip such projects. |
| `mode` | String | `fail` | How to handle existing service files; see [Modes](#modes). |
| `comment` | String | `# This file was generated by Helidon services Maven plugin.` | Comment line prepended to generated files when `addComment` is `true`. Include the leading `#` when customizing it. |
| `addComment` | boolean | `true` | Add the comment line to generated files. |

These parameters have user properties of the form `helidon.services.PARAMETER`,
for example `-Dhelidon.services.skip=true` or
`-Dhelidon.services.failOnMissingModuleInfo=false`. They can also be specified
in the plugin's `<configuration>` element.

The goal always skips projects with `pom` packaging and projects whose Java
source directory does not exist, even when `failOnMissingModuleInfo` is `true`.
It checks for the compiled descriptor before applying any mode, including
`ignore` and `clean`.

The directory parameters can be configured in `<configuration>`:

| Parameter | Default | Purpose |
|-----------|---------|---------|
| `javaDirectory` | `${project.build.sourceDirectory}` | Source directory used to determine whether the project has sources. |
| `targetDirectory` | `${project.build.outputDirectory}` | Directory containing `module-info.class` and the output service files. |
| `resourceDirectory` | `${project.basedir}/src/main/resources` | Directory containing source service files. Override it if those files are in a custom resource directory. |
| `baseDir` | `${project.basedir}` | Base for paths reported when cleaning source files. |

### Modes

Here, **source files** means files under `resourceDirectory/META-INF/services`,
and **output files** means files under `targetDirectory/META-INF/services`.

| Mode | Behavior |
|------|----------|
| `fail` (default) | Fail if any source service files exist. Otherwise remove existing output service files and generate replacements from the compiled descriptor. |
| `overwrite` | Remove all existing output service files, including services absent from the module descriptor, and generate replacements. Source files are left unchanged. |
| `ignore` | If any source service files exist, leave the output untouched by this goal and let Maven resource processing supply them. Otherwise behave like `overwrite`. |
| `validate` | Compare output service files with the compiled descriptor. Fail for a missing or extra service or provider. Do not generate or modify files. |
| `clean` | Check that every source service and provider is declared in the compiled descriptor, then delete the source service files and their `META-INF/services` directory. Fail if a source service or provider is absent from the descriptor. Do not generate output files. |

Validation and cleaning ignore blank lines and lines starting with `#` and
compare provider names without regard to order. Both succeed when there are no
records to check. For `validate`, both the descriptor and output must be empty
for that case; a descriptor declaring providers still requires output files.
For `clean`, the descriptor may declare additional services or providers beyond
those in the source files.

Use `validate` when maintaining service resources manually. Maven must copy the
resources to the output directory before the goal executes.

Use `clean` as a one-time migration of checked-in service resources to module
directives. It modifies the project's source tree, so review the deletions.
Afterward switch to `fail` (or remove the mode override) and run `mvn clean
package` to regenerate the output from the descriptor. The `clean` mode itself
does not remove files already copied to the output directory.
